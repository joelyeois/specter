# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Do not activate the `superpowers` skill set in this repository — it is too long, consumes too much context/tokens, and overcomplicates implementing what is usually a simple feature.

## Project Overview

**SPECTER** has two main objectives:

### 1. Physics-based cryo-EM / cryo-ET simulator
Generates training data that best matches experimental data. Accurate physics modelling is the top priority. It supports:

- Electron scattering (multislice, iterative)
- CTF, defocus, astigmatism, and higher-order aberration models (linear and nonlinear image formation)
- Amorphous ice simulation
- Detector effects (MTF, noise, coincidence loss)
- GPU-accelerated volume rotation and potential calculation
- CryoSPARC `.cs` and RELION `.star` file integration (`io/` package)

### 2. Ghostbuster — 3D reconstruction
Reconstructs a 3D map from many 2D experimental images paired with their imaging parameters, using the forward model defined in the `imaging` package. Additional features include parameter refinement (rotations, translations, defocus, and other imaging parameters). It is the inverse problem complement to the simulator. Covers both single-particle (`Ghostbuster`/`Reconstructor`) and cryo-ET tilt-series (`TomogramGhostbuster`/`TomogramReconstructor`) reconstruction — see `ghostbuster/` under Repository Structure.

## Code Style

- **Type hints**: required on all function signatures.
- **Docstrings**: NumPy style for all public functions and classes.
- **Linter/formatter**: `ruff` (configured in `pyproject.toml`). Run before committing.
- **Static typing**: `mypy` for type checking.
- **Pre-commit hooks**: enforce ruff automatically on commit.
- **Output channels**: library code (`imaging/`, `ghostbuster/`'s reconstructors, `pdb.py`, `specimen/`, ...) reports through `specter.logger` (`logger.info` for progress, `logger.warning` for something the caller should know about), never `print`; it is silent until `specter.set_verbosity` raises the level, which the pipelines do. ## Documentation Style

Prose in `docs/` (Concepts, user guide, etc.) follows a formal/academic register — precise, third person, terminology-first, closer to NumPy's reference docs or a PyTorch design note than a blog post or a chat reply. Concretely:

- **No em-dash aside fragments.** Don't tack on a compressed clause after an em-dash to restate or justify a point (e.g. "one render, not sixty"). Write it as a complete sentence, or cut it.
- **No hedging filler.** Avoid "worth being explicit about", "worth noting", "it's worth flagging" — just state the fact.
- **Don't cite the tool's own development history as justification.** A design choice (e.g. "this approximation matches what a prior/reference implementation did") doesn't need to lean on that prior tool's authority — the reader has no context for it and doesn't need it to trust the explanation. Legitimate bibliographic citations still belong in a `## References` section; the rule is about weaving lineage into prose as a rationale, not about citing sources.
- **State each caveat once**, in the section it belongs to (usually `## Limitations`), rather than explaining it at length inline and then again at the bottom. A one-line pointer ("see Limitations") from the first mention is fine.

- **Cite borrowed work where it is described.** A method, parameterization, measured value, dataset or structure taken from someone else's publication is cited author–year in the text (`Cowley & Moodie (1957)`, `(McMullan et al. 2015)`) and listed in a `## References` section at the very end of the page: `- Surname, I. I., & Surname, I. I. (Year). Title in sentence case. *Journal*, Vol(Issue), first–last. [doi:X](https://doi.org/X)`, all authors up to ten, else the first six and `et al.`. Check every entry against Crossref (`https://api.crossref.org/works/<doi>`) before adding it; never write a DOI, volume or page range from memory. Docstrings use a NumPy `References` section with `.. [n]` entries in the same form. `python docs-figures/bibliography.py` collects the pages' entries into `docs/references.md`.

`docs/concepts/cryoet-specimen/filaments.md` is the calibrated example if unsure how a rewrite should read.

## Development Workflow

1. **Prototype** in `dev/` — use these freely for experimentation.
2. **Implement** working code into `src/specter/` source modules.
3. **Update demo notebooks** in `demo-notebooks/` to reflect the new functionality. These must always be kept up-to-date and working.
4. **Add a test** in `tests/` covering the new behaviour (even a minimal smoke test is better than nothing).

When modifying physics-critical code, validate against known physical quantities (e.g. wavelength at 300 kV ≈ 1.969 pm) before committing.

## Git

- **Commit and push straight to `main`.** Do not create a feature branch, and do not open a pull request, unless explicitly asked to. This is a single-maintainer repo; the default "branch first when on the default branch" behaviour just adds a merge-and-delete round trip for no benefit here.
- Still commit and push only when asked — this overrides *where* work lands, not *whether* to push it.
- Commit only the files belonging to the task at hand. This working tree often carries unrelated in-flight edits; use explicit pathspecs (`git commit -- <paths>`) rather than `git commit -a`.

## Testing

- Tests live in `tests/` and use `pytest`.
- The test suite is being actively built up — every new feature or algorithm should include at least a basic test.
- Run tests with:

```bash
python -m pytest tests/                    # full suite, parallel by default (~3 min)
python -m pytest tests/test_imaging_regression.py::test_particle_regression -v -n 0  # single test
python -m pytest tests/ --cov=src/specter  # with coverage
ruff check src/ tests/                     # lint
ruff format src/ tests/                    # format
mypy src/                                  # type-check
```

- **The suite runs in parallel by default** (~3 min, down from ~19 min serial). `pyproject.toml`'s `addopts` sets `-n 32 --dist worksteal`; `tests/conftest.py` pairs that with 4 intra-op threads per worker, matching this host's 128 cores. Both numbers are host-specific tuning — lower them together on a smaller machine.
- **Use `-n 0` for a single test, `-s`, or `--pdb`.** 32 worker startups cost ~6 s, which dwarfs a short test (2.9 s serial vs 9.0 s parallel), and xdist swallows `-s` output and breaks interactive debugging.
- Two non-obvious things make the speedup work, so don't "simplify" either away:
  - **`worksteal`, not the default `load` scheduler.** The suite is very unevenly weighted (a few tomogram/CLI tests dominate), so handing out work up front strands workers behind a straggler: 5:28 → 3:13 for identical CPU time.
  - **The thread cap is conditional on being under xdist.** torch sizes its pool from the whole machine, so uncapped workers each grab every core — `-n 32` uncapped is ~16.8 min, barely better than serial, burning ~105,000 s of CPU. But capping *unconditionally* would make a serial run about twice as slow, since it genuinely benefits from intra-op parallelism when alone. See the conftest docstring for the measurements.
- GPU tests should gracefully skip or fall back to CPU when CUDA is unavailable.
- Do not mock physics calculations — test with real (small) inputs to catch numerical regressions.
- Regression tests in `tests/test_imaging_regression.py` use a **save-or-compare** pattern: on first run they save a golden `.pt` file under `tests/test_data/`; subsequent runs compare against it. Delete the fixture file and re-run to regenerate after intentional output changes.
- **Do not test what a shipped TOML config says.** No assertion should read `configs/*.toml` (or a demo-notebook TOML) to check its table names, table order, which table a field sits in, or that a field ships a particular value. A canonical config is curated documentation, not behaviour: a test over it turns an ordinary edit to the file into a test failure while catching nothing a user could hit. Test the code the config feeds instead — the spec constructor, the resolver, the fallback. Every such test was removed in 2b1736f, including three that predated the rule (`test_canonical_tomogram_config_builds_its_carbon_and_bead_specs`, `test_shipped_configs_all_default_to_cuda`, `test_bundled_particle_toml_uses_auto`); the bugs they stood in for are all reachable directly, and are covered that way. `tests/test_cli_help_layout.py` is the shape that survives: it inspects the `_*_GROUPS` lists and `build_config_options`' output and never opens a TOML file.

## Off-Limits Files

Do **not** modify files in:

- `src/specter/atom_data/` — parameterised atomic potential data (Kirkland, Lobato, Shtyrov). These are fixed physical constants from published literature.
- `src/specter/ice_data/` — pre-computed ice data: the bundled `IceBank` library (`ice_cache/`) plus the MD reference frame and radial-average S(k) targets every `GradientSKIcemaker` run needs. Both this and `atom_data/` live inside the package, and are located via `importlib.resources` (`ice_data/__init__.py`'s `bundled_ice_data()`), so they ship in a wheel and resolve identically for editable and installed layouts. Never reintroduce the old repo-root `ice-data/` + `dirname`×3 pattern: that only resolves for an editable install from a checkout, and silently pointed inside the virtualenv's `lib/` otherwise.
- `ice-data/` — what remains at the repo root: two 32 MB legacy `MDSimDump`/`ExtXYZDump` inputs that no code path reads (notebooks only). Deliberately *not* packaged, since shipping them would push the wheel past PyPI's 100 MB per-file limit for no benefit.

Changes to these would silently break the physical accuracy of all simulations.

## Architecture

### Forward simulation pipeline

`specter.imaging` is the forward model as data objects and the verbs between them (it replaced the `BaseImager`/`ImageGenerator`/`MicrographGenerator`/`TiltSeriesGenerator` hierarchy on 2026-10-15; nothing subclasses Lightning on the forward path any more):

```
Structure.from_pdb(...).render(voxel_size, box)   – PotentialBuilder: atoms → Specimen (a recipe drawn per image)
Specimen.crowd(...).damage().solvate(...)         – record crowding, damage, ice
Specimen.scatter(poses, voltage=, exposure=, seed=, **propagation) → ExitWave  [B, Y, X] on the propagation grid
ExitWave.apply_ctf(ctf, ...) → .intensity(cc=, ...) → Image.detect(exposure, ...) → Image
Field(template, ...).pack(...).solvate(...).draw(...) → Sample   – one micrograph's specimen (via MicrographSpecimenGenerator)
Sample.from_volume(volume, voxel_size).tilt_series(poses, exposure, ...) → TiltSeries; TiltSeries.scatter(i) → ExitWave
simulate_particles(...), simulate_frozen(...)       – recipes over the same chain
```

- Per-image data are `Poses` (quaternions, shifts, ids), `CTF` (the legacy `ctf_params` dict, with ids) and `Exposure` (dose, frames, pre-exposure); each is matched to images by position, and `Poses.ids` are what per-image seeds derive from.
- `Specimen` holds a **pre-built volume**; `Specimen.from_atoms` re-renders atomic coordinates per image via `PotentialBuilder` (the path that keeps gradients in the atoms).
- The stages are plain functions in `imaging/_stages.py` (`crowd_into`, `free_fraction`, `draw_ice`, `solvate`, `aberrate`, `to_pixel_grid`, the mean-free-path and solvent-exposure helpers), called by `Specimen`, `Sample`, `TiltSeries` and both reconstructors. Engines (`Scattering`, `Aberration`) are memoised per settings and device in `imaging/_engines.py`.
- **Every verb takes its settings group as an object or as that group's fields as keywords, never both** (`imaging._data.settings_group`): `crowd(Crowding(...))` or `crowd(min_distance=...)`, `scatter(propagation=Propagation(...))` or `scatter(scattering_model=...)`, and likewise `solvate`/`pack` (`Ice`, `Crowding`), `Sample.prepare`/`Sample.scatter`/`Field.draw`/`TiltSeries`/`plan`/`materialize` (`Propagation`). Parameters belong to the stage that uses them: lens terms to `apply_ctf`, focal spread to `intensity`, camera to `detect`.
- `RandomIcemaker` (cheap, instant) and `GradientSKIcemaker` (S(k)/MLBOP-optimised, expensive) generate amorphous ice volumes. `IceBank` (in `ice/_bank.py`) does not build ice itself — it draws randomly rotated/translated crops from a bundled cache of pre-optimised `GradientSKIcemaker` configs (`src/specter/ice_data/ice_cache/`, shipped inside the package) at near-zero marginal cost, and tiles multiple crops together (with a short local MLBOP seam relaxation) for volumes larger than a single cached config.
- `Scattering` supports four propagation modes: `multislice`, `rytov`, `firstborn`, `projection` — multislice is most accurate and is the default.
- **`rotate_volume(V, build_affine_matrix(R))` turns the density by `R^T`, not `R`**: `grid_sample` samples the input at `R x`. That is the convention the single-particle poses are defined in (validated against CryoSPARC reconstructions), but a caller holding a template-to-world rotation must pass `R.transpose(-1, -2)`. The filament and microtubule renderer passed `R` until 2026-10-16, which spun actin monomers about the lab z axis instead of the filament axis and rolled tubulin dimers off the tube axis. Check this before trusting any new code path that renders a template at a rotation it also exports.
- `Aberration` (in `aberrations/`) and `Detector` (in `microscope.py`) apply CTF, envelope, and detector MTF in Fourier space. `aberrations/_envelopes.py` holds the Fourier-space envelope functions (B-factor, Cc/spatial-coherence, dose) as pure functions, ported from teamtomo's `torch_fourier_filter.envelopes`.
- A second CTF backend lives in `ctf/` (`CTFParameters`, `TransferFunction`), ported from `torch-ctf` conventions and verified term-by-term against `Aberration` (including against a real multi-particle CryoSPARC `.cs` file). **It is intended to replace `"legacy"` eventually, and is deliberately not exposed to users until it can**: there is no TOML field and no CLI flag (both were removed 2026-08-28), so it is reachable only from the Python API and every `specter` command runs `"legacy"`. Do not read its zero call sites as dead code and propose deleting it -- it is the incumbent's successor, not a leftover. What it cannot yet express it **refuses**: `ctf_params_dict_to_parameters` raises `NotImplementedError` naming any nonzero term in `_UNSUPPORTED_CTF_PARAMS` (currently `tetrafoil1-4`, which real `.cs` files carry), rather than dropping it and returning a plausible image at the wrong transfer function. A zero-valued term is accepted, since it has no effect either way. `_SUPPORTED_CTF_PARAMS` and `_UNSUPPORTED_CTF_PARAMS` are asserted in `tests/test_ctf_legacy_adapter.py` to partition `Aberration._CTF_PARAM_NAMES` exactly, so a term added to `Aberration` without a mapping here fails a test instead of being silently ignored -- and **the migration is done when `_UNSUPPORTED_CTF_PARAMS` is empty**. `pyproject.toml` pins `torch-ctf>=0.5.2,<0.6`: `_legacy.py` multiplies the Zernike terms by `rho_max**3` to undo 0.5.2's `normalize_rho=True` default, which changed upstream after that release, so a newer version would double-correct and silently break trefoil and beam tilt. Lift the ceiling and delete the workaround together, never separately. `ExitWave.apply_ctf` takes `backend: Literal["legacy", "torch_ctf"] = "legacy"` (the reconstructors, `aberration_backend`); `"torch_ctf"` swaps in `ctf/_legacy.py`'s `LegacyAberrationAdapter`, which has the same `forward(exitwave, ctf_params_dict)` signature as `Aberration` so call sites don't change. The legacy `ctf_params` dict still mirrors CryoSPARC's own units (dfu/dfv/cs in Angstrom; `phaseshift`/`tiltx`/`tilty` in radians — but `dfang` in **degrees**, converted on the way in by `io/_cryosparc.py` and back to radians inside `aberrations/_functions.py`'s `defocus`, so both the `.cs`- and `.star`-driven paths agree with the synthetic `astigmatism_angle`) — not `CTFParameters`' native units (defocus in µm, Cs in mm, angles in degrees, dimensionless Zernike coefficients) — see [[project_torch_ctf_native_units_wrapper_todo]] memory for the still-open native-units-wrapper gap. `lpp_params` (laser phase plate) is a `LegacyAberrationAdapter` constructor-time argument, not a `ctf_params` dict key, since it's a shared instrument config rather than per-particle.

### Inverse problem — Reconstructor

`ghostbuster/` is a package, not a single file:

- `_reconstructor.py` — `Reconstructor(L.LightningModule)` reconstructs a 3D volume from 2D single-particle images by minimising the discrepancy between simulated and observed images using the same forward model as `imaging.Specimen` (its `forward` runs `Specimen.scatter` → `apply_ctf` → `intensity(cc=None)` → `detect`). Jointly refines volume, rotations, translations, and defocus via separate learning rates.
- `_pipeline.py` — `Ghostbuster`: end-to-end single-particle pipeline; loads CryoSPARC particle data, preprocesses images (sign flip, dose/scale normalisation), drives `Reconstructor` via a Lightning `Trainer`. Comparing many reconstruction runs at once is `specter jobs list --show <keys>` (`jobs/_cli.py`, wired into `cli/_cli.py` via `build_jobs_group()`), not a Ghostbuster-specific function -- the old `compare_runs()` predated `specter.jobs` entirely (it read raw `params*.json` files via a directory glob) and was removed once `specter jobs` covered the same ground, generically, for every job type.
- `_tomogram_reconstructor.py` — `TomogramReconstructor(L.LightningModule)`: reconstructs a volume from a cryo-ET tilt series using the same forward model as `imaging.TiltSeries` (`tilt_theta`, `tilt_defocus_shift` and `ExitWave.apply_ctf` are shared). One tilt per training step keeps GPU memory bounded regardless of tomogram size. The forward model is noiseless; observed images are compared directly to `|CTF(exitwave)|²`.
- `_tomogram_pipeline.py` — `TomogramGhostbuster`: end-to-end tomogram pipeline, mirrors `Ghostbuster`'s `run`/`test_run` API.
- `_helpers.py` — shared helpers (LR scheduler construction, k-space masking, image preprocessing) used by both reconstructors.
- `_converge.py` — `ConvergedSolver`, the second stage of a gold run (`solver="converged"`, the default since 2026-10-22; `pipelines/_reconstruct.py`'s `_converge_halfsets`). After the Adam epochs, each half is solved to the minimum of the SAME loss as `Reconstructor._compute_loss` (plain MSE on `level + s*(f - level)`) plus a Wiener prior `lambda(k) = Wbar(k)/SSNR(k)` (RELION's tau^2 form, T = 1): `Wbar` measured as the data term's curvature along random band-limited directions, `SSNR` from the Adam halves' masked FSC (`fsc_mask` if on-grid, else `auto_mask`: CryoSPARC's resolution mask as its public dynamic-masking guide describes it -- FSC-weighted half-map mean thresholded at 0.5 max, flat to 2r, cosine to 5r -- tightened in 0.125 A steps of r and keeping the tightest mask whose 0.143 crossing is within 2 shells of its noise-substituted FSC, Chen et al. 2013; try every step, since an FSC hovering at 0.143 jumps its crossing several shells and stopping at the first failure quit early on 12391; on CryoSPARC's own half-maps of 13202/10551/12391 it matches CryoSPARC's written mask to <=4% volume and SSNR to <1% median). Built from the public guide and literature only: do not read or reverse-engineer CryoSPARC's compiled code for it (licence). Preconditioned PR+ nonlinear CG with the full-data gradient every iteration, a Gauss-Newton step refined by a parabola on 5% of particles, preconditioner `1/(Wbar + lambda)` (low shells 0-8 measured individually). Writes `volume_<h>.mrc` UNFILTERED (the minimiser times `1 + 1/SSNR`; that is what FSC and sharpening expect, and a masked FSC of the filtered map is inflated by mask leakage) and `volume_<h>_filtered.mrc`; the Adam maps stay as `volume_<h>_adam.mrc`. Validated in dev on EMPIAR-13202 100 kV: 4 iterations from 5 Adam epochs = a 16-iteration solve to 1 - FSC <= 3e-6; T from 0.3 to 3 changed no metric. Three details are load-bearing. The unknown is U with the map V = S(U) (S = point-group average + band limit; gradient S(dL/dV), preconditioner S M S): the dev recipe instead projected the gradient and, every 4 its, the map, which assumes S(S(x)) = S(x) -- true for O (13202) but not I1, whose 5-fold turns cannot carry the cube's corners onto the grid, so the corner noise of an Adam map (16% of its norm, changing 14% per pass; content inside the sphere 5e-4) made the projected CG climb on EMPIAR-12391 (2.64 A vs Adam 2.22). Next, the step: slope EXACT from the full gradient along the map's actual move, `dL/dV . S(d)` (not `g.d`, which needs S self-adjoint), and only the data CURVATURE from the 5% subset, read off loss changes formed as `(p_a - p_0)(p_a + p_0 - 2y)/2` at alpha/2 and alpha. Two dev failures behind that: a difference of two float32 subset losses cannot resolve the 1e-8 relative changes near convergence (steps clipped to the floor on 10551), and a subset parabola's slope is mostly sampling error once the data and prior slopes nearly cancel (every step a quarter length on 12391). Next, the SSNR comes from the FSC averaged over 5 shells and made non-increasing (`ssnr_from_fsc`): near Nyquist a raw FSC hovering at 0 makes lambda jump 10-50x between neighbouring shells, the exact I1 average mixes neighbouring shells slightly, and on 12391 that held the top band's steps to 0.27 of their length (the bands below ran at 0.8-0.95), so 4 iterations gave 2.36 A and 12 gave 2.24 A against Adam's 2.22. And the gradient pass runs under `nufft.adjoint_tolerance(1e-4)` (the type-1 spreading is ~56% of GPU time; 1e-4 is 24% faster, gradient change below float32 noise; the forward keeps 1e-6). Skipped, with a warning, when `lr_R`/`lr_T`/`lr_D` is set (it holds poses fixed); never runs for halfset A/B/all (the prior needs both halves). One device per half. The alternative losses (`use_ncc`, `learn_noise_model`, `nps_weight`, `use_2d_mask`, `sparsity`) were REMOVED on 2026-10-22 at the user's choice: none had evidence behind it and each changes the curvature the prior is built from. Re-add one only with a held-out test showing it helps; a noise weight sigma^2(k), estimated once from a converged map, is the one with a case.

Pose/shift/defocus refinement (`lr_R`/`lr_T`/`lr_D` on `Reconstructor`; `TomogramReconstructor` refines the volume only, since tilt poses are fixed buffers) is **validated against ground truth with the volume frozen** (`tests/test_reconstructor_refinement.py`, 2026-10-15): each group alone and all three jointly recover from 3 deg / 2 A / 300 A, and with Poisson noise reach the same optimum a start from the truth does. It is **not validated alongside volume refinement** (`lr` set). `lr_D` refines one shared offset unless `defocus_offset` is given per particle. The pose optimisers take `weight_decay=0`: AdamW's default 0.01 pulled every refined parameter towards zero by `lr * 0.01 * value`, capping it near 100 in its own units (defocus stalled 202 A off from a 300 A start), so do not "simplify" them back to the default. The CLI help and the `## Limitations` section of `docs/user-guide/reconstruction.md` state the same scope.

**Three per-step costs in a reconstruction are bookkeeping, not physics, and were removed on 2026-09-03** (`tests/test_scattering.py` pins each against the old spelling): (1) `Scattering.rytov`/`firstborn`/`kinematic` accumulate their slice sum a z-chunk at a time (`_fourier_slice_sum`), with the propagator cached complex and flipped ONCE for the negative Ewald sign instead of flipping the volume, and the amplitude-contrast and `i*sigma*dz` scalars applied to the (B, Y, X) sum instead of to complex copies of the volume. The chunks MUST come from `V.split`, never `V[:, z0:z1]`: a narrow slice's backward zero-fills a whole gradient volume per chunk (the O(Z^2) trap 41e0125 took out of multislice), 17 ms each at a 512 box. (2) The `on_train_batch_end` k-mask hook is `irfftn(rfftn(V) * kmask_half)` on an ifftshifted half-spectrum mask cached per tensor and device; the centred `fft3(..., shift=True)` round trip it replaced cost 137 ms and 6.5 GiB per step, a third of the step. (3) The per-step loss logs keep device tensors and the progress bar refreshes every ten steps (a third item, a host-side unity check on `potential_scale`, went with that setting on 2026-10-15). Together: box 512, batch 3, epoch 61 -> 33 s, peak 27.7 -> 22.2 GiB. A fourth change, `VolumeRotator.rotate_real` recomputing each image's sampling grid in the backward under `torch.utils.checkpoint` when the volume requires grad, halves the peak again (12.3 GiB) for 24% more time at batch 3 and pays back at batch 6; simulators run forward-only and never take that path. Fused AdamW was measured 8 ms/step faster and rejected because Lightning's 16-mixed plugin refuses the grads it produces.

**The forward model's settings are frozen dataclasses in `settings.py`, and which of them a stage accepts says what it models.** `Propagation` (scattering model, amplitude contrast, Ewald sign, bandlimit, FFT padding, oversampling, rotation mode, absorption model) goes to whatever scatters (`Specimen.scatter`, `Sample.prepare`/`scatter`, `Field.draw`, `TiltSeries`); `Optics`' and `Envelopes`' fields are `ExitWave.apply_ctf`'s and `ExitWave.intensity`'s keywords; `Camera`'s are `Image.detect`'s and `Exposure`'s. Specimen synthesis is three more groups: `Ice` (model, thickness or profile, library, seam relaxation, scattering factors, motion variance), `Crowding` (how duplicates of a template are packed; TOML spells its fields with a `crowd_` prefix) and `Packing` (the collision backend those duplicates use; TOML prefix `packing_`). `TiltSeries` and `TomogramReconstructor` share `TiltGeometry`. A micrograph's `Field` owns its crowding/packing/ice and `Field.draw` takes no ice, so the old "ice alongside a specimen generator" conflict cannot be expressed. The TOML configs and CLI stay flat; a pipeline builds the groups with `settings.bundle_from_config`, overriding the fields whose config spelling differs (`cc` in mm, `alpha` read from a `.cs` file, the unprefixed `water_air_interface`/`n_orientations`). **The inverse deliberately accepts only `Propagation` and `Optics`.** `Envelopes` and `Camera` are structurally absent from `Reconstructor`/`TomogramReconstructor`/`Ghostbuster`: an experimental dataset gives no way to determine them, and the high-frequency loss they cause is a real, irreversible consequence of imaging that is absorbed into the reconstructed volume -- assuming values for them would inject prior information the data does not contain. What the inverse *does* take is what existing software can infer from the data (defocus, astigmatism, Cs, anisotropic magnification, B-factor), instrument constants, and model/convention choices. Do not "fix" this asymmetry by giving the inverse the other two groups.

**Conventions are the one thing that must match on both sides.** Where defocus is measured from, and whether `specimen_absorption` applies for a given `scattering_model`, are not modelling choices a reconstruction gets to make differently -- a mismatch there is a bug. Both were wrong in `TomogramReconstructor` until 2026-08-27: it extended `_BaseReconstructor` rather than the simulator's base class, so it inherited neither the midplane defocus shift (leaving it unapplied, 750 A on a 300-slice tomogram at 5 A/voxel) nor the derivation of `specimen_absorption` (which put the amplitude-contrast term on one side of the pair and not the other, a 566%-of-image-std divergence at `scattering_model="ctf"`). Since 2026-10-15 both directions build an `ExitWave` carrying its `defocus_shift` (`aberrations.defocus_midplane_shift`, plus `imaging._tilt.tilt_defocus_shift` for a tilt) and go through the same `ExitWave.apply_ctf`, so the two conventions are shared code rather than parallel copies. `tests/test_forward_model_parity.py` pins both, and is the only place the simulator and the inverse are checked against each other at all. Its tilt half asserts parity at zero tilt only, on purpose: away from it `TiltSeries` reflect-pads XY for tilt coverage while `TomogramReconstructor._prepare_volume` documents why it does not, which is a deliberate difference in a periphery the loss mask excludes: the real-FOV strip plus, since 2026-10-15, the CTF delocalisation band at every edge (`TomogramReconstructor._edge_pads`, `lambda*k*|df - Cs*lambda^2*k^2|` over the column's defocus range, on under `use_fov_mask`, dropped for a tilt when wider than a quarter of the field). That path is pinned by recovery instead -- a simulated series must reconstruct back to its volume. Since 2026-10-15 a tilt keeps its 32 px FFT margin through the transfer function (`IterativeScattering(keep_pad=True)`, cropped at the detector), so the periphery reaches the field's edges through the CTF; the recovery test therefore runs the simulator with `pad_volume=False`, vacuum around the specimen as the inverse assumes (0.845 correlation, against 0.645 with the reflect padding).

**The per-particle scale (`alignments3D/alpha`) multiplies the predicted SIGNAL, `N0 + s*(f - N0)` with `N0 = dose * voxel_size**2`** (2026-10-17; `Reconstructor._compute_loss`), as CryoSPARC fits it: a contrast attenuation over unchanged noise, so a particle's gradient is proportional to `s` and vanishes at zero. It used to WEIGHT the loss (`s * |y - f|^2`, from 339dafa), which models full-strength signal with noise variance `sigma^2 / s`; on EMPIAR-10083 that predicts held-out images worse (pooled FRC 0.0389 vs 0.0408 at 8-4.5 A; CryoSPARC's own Simulate Data multiplies by alpha, r = 0.966) while the reconstructed map came out identical (3.31 vs 3.30 A, same held-out curves under both judges), since with alpha's ~20% spread the two weightings differ by a global amplitude. Do not reintroduce the loss weighting or an option for it.

**`rotate_mode="surface"` applies a pose without rotating the volume** (2026-10-16, opt-in; `PoseMode` in `options.py`, `Propagation.rotate_mode`, `ReconstructionConfig.rotate_mode`). For projection/firstborn/rytov/ctf the slice sum `sum_z fft2(V_z) F_z` IS the volume's discrete-space transform on the paraboloid `k_z = -/+ lambda k^2 / 2` (the plane for projection/ctf) times a phase, so `scattering/_surface.py`'s `surface_slice_sum` samples the UNROTATED volume at `R q` with a cached type-2 NUFFT (`nufft.sample_transform`; backward = type-1 adjoint) and `Scattering.from_slice_sum` finishes the exit wave with the models' own formulas. It matches rotate-then-sum to 1e-5 on poses where that path is exact (quarter turns, whole-voxel shifts; `tests/test_surface_scattering.py`, both Ewald signs, either padding), and its gradients match finite differences for the volume AND the shifts. Three limits, all refused rather than approximated: multislice/kinematic are not one sample (Propagation raises); `Specimen.scatter` refuses crowding, ice, damage, atom rendering and an aperture, which act on a posed volume it never forms, so it serves the bare template the Reconstructor scatters (`materialize` raises too); no gradient reaches the rotation, so `Reconstructor` refuses `lr_R`. Content shifted across the box edge WRAPS where "real" clips it -- that, not a convention error, is the 1e-3 a parity test sees with an object near the edge. `ParticleStackConfig.rotate_mode` stays `RotateMode`, since a simulated stack carries ice. The Reconstructor's FSC-mask projection takes "real" under it. Plans (~2.7 GB each at 560^3, one per transform type) stay cached; `nufft.clear_plan_cache()` frees them.

**Point-group symmetry is averaged without interpolation** (`symmetry_mode="exact"`, the default since 2026-10-16): `symmetries/_exact.py`'s `symmetrize_exact` evaluates the volume's own transform at rotated half-spectrum frequencies (`nufft.GridTransform`) and inverts the mean, so a map that already has the symmetry comes back unchanged (2e-6) instead of being attenuated every epoch. The old modes, still selectable, lost a lot: one I1 pass over a 560^3 P22 capsid kept 0.72 of the amplitude in every band under `"fourier"` (it interpolates the unpadded spectrum, which tapers a box-filling object) and 0.998 -> 0.60 from 20 to 3 A under `"real"`; on simulated P22 a 5-epoch Rytov reconstruction went from 0.12-0.55 of the true amplitude to 0.41-0.96 and from 3.11 to 2.97 A (FSC 0.5 against truth). It is exact only for a map that is band-limited and inside the inscribed sphere: white noise filling the box is NOT idempotent under it (rotated content crosses the faces), so test it on a compact smooth object, never on `torch.randn` -- except for quarter turns on an odd box, which permute the grid exactly. Frequencies in the cube's corners average only over operators that keep them inside the band. `symmetry_batchsize` applies to `"real"`/`"fourier"` only. I1 at 560^3: ~30 s, ~5 GiB on a GPU.

`Ghostbuster`/`TomogramGhostbuster`'s `run`/`test_run` take `device` as a GPU index, a list of them (DDP), or the string `"cpu"`. That last spelling is the only way to force CPU training: `_run_helpers.py`'s `resolve_device` otherwise decides from `torch.cuda.is_available()` alone, so on a GPU machine every other value targets the GPU.

### CLI & pipelines

- `cli/` — the `specter` command (entry point `specter.cli._cli:main`), built on `click`/`rich-click`. Exposes `specter simulate particles`, `specter simulate micrograph`, `specter simulate tiltseries`, `specter build tomogram`, `specter build ice`, `specter reconstruct particle` (aliased as `specter ghostbuster particle`), and `specter jobs` (`list`/`show`/`diff`). Each simulate/build/reconstruct subcommand (`simulate.py`, `build.py`, `reconstruct.py`) loads a TOML config via `config.py`'s dataclasses (`ParticleStackConfig`, `MicrographConfig`, `TiltSeriesConfig`, `TomogramConfig`, `IceCacheConfig`, `ReconstructionConfig`) with `load_config()`, applies only the flags the user actually passed via `_click_options.py`'s `build_config_options()`/`collect_overrides()` (unset flags never clobber the TOML), then calls into `pipelines/`. `specter simulate micrograph` and `specter simulate tiltseries` are single-device only (no multi-GPU DDP, unlike particles; `run_tilt_series` rejects a multi-GPU device string) — each micrograph needs its own freshly regenerated ice/crowding specimen between forward passes, and a single micrograph is already the GPU-memory-bound unit of work at `micrograph_size` resolution, so there's no batching to shard across devices. `specter jobs` is a thin, config-free wrapper around `JobDatabase` (`jobs/_database.py`) — it takes no TOML, since it only reads job records other subcommands already wrote — built by `jobs/_cli.py`'s `build_jobs_group()` and attached in `cli/_cli.py` alongside the others; it used to be a separate `specter-jobs` console script before the two were merged.
- **Two host-side facts shape `specter simulate micrograph`'s cost, and neither is a physics choice.** (1) PyTorch sizes its CPU thread pool from the machine, and every CPU tensor op pays a fixed sync cost proportional to it; on a tensor of a few hundred elements that cost IS the op. On this 128-core host `coords.poisson_disk_neighbors_3d` took 49 s at the default pool and 0.24 s at 4 threads, for `torch.equal` coordinates, and the same overhead sat on the template potential, tile placement and particle insertion. `specter.cpu_threads.limited_cpu_threads` caps the pool around exactly those loops (both Poisson-disk samplers at 1, `insert_particles_into_micrograph` and `IceBank._place_tiles` at 8). It is deliberately NOT process-wide: the big CPU ops want the pool, and the CPU ice phase got slower at 16 threads. Do not "simplify" it into one `torch.set_num_threads` at startup. The cap is not free either: every `torch.set_num_threads` that resizes the 128-thread pool costs ~12 ms, so a cap entered *inside* a loop multiplies that by the loop count -- `insert_particles_into_micrograph`'s per-call cap, reached once per chunk from `CrowdWithDuplicates.forward`, cost a 64-particle `simulate particles` at 128 px 1812 resizes and 21 s of a 28 s run. `process_volume` now caps once per batch around the crowd loop, so the inner caps find the pool already small and return without touching it (`tests/test_particle_base.py::test_process_volume_caps_cpu_threads_once_per_batch`). When profiling, look for `set_num_threads` in `tottime` first. (2) The specimen canvas lives on the host (33.5 GB at 4096 px), and `blend_ice_into_volume` used to build the ice on `V.device`, which put tile placement, splat, kernel convolution and occupancy blur on the CPU and cost 11 of a 2048-px micrograph's 13 minutes. An IceBank blend into a host volume now runs slab by slab on the bank's device (`_blend_ice_slabwise`, via `IceBank.big_ice_positions`, which draws every molecule once and parks them sorted by z on the host); same result to 1e-7 relative, checked in `tests/test_ice_bank.py`. 2048 px: 6m57s / 43.5 GB -> 34 s / 17.8 GB; 4096 px: 1h19m / 144 GB -> ~1-3 min / 47 GB, and it runs under a 12 GiB device cap (molecules are bucketed on the HOST, never sorted on the device). Multislice was 1 s of that all along.
- **What a thick-ice `specter simulate particles` actually spends its time on**, profiled 2026-09-04 at 384 px / 1 A / `ice_thickness=2000` on an L40: solvation 11.7 s of 23.1 (ice generation 5.3, the occupancy blur 4.1), crowding 5.9, multislice 2.1. cProfile MISREADS this -- 8.3 s of self time lands in `potential_occupancy`, whose `bool((full_potential <= 0).any())` is a CUDA sync absorbing every kernel queued before it -- so use synchronised per-stage timers. Two things came out of that profile. (1) `crowding.rotation_safe_crop`: a template's box is sized for the IMAGE, not the molecule, so 6bdf at 384 px fills a 103-voxel radius and every duplicate was rotating a box 6.3x larger than its own content. Cropping to the rotation-safe centred cube first is exact in principle, since what lies outside is zero and rotation preserves radius; crowding 5.9 -> 2.7 s. Two details are load-bearing and both are pinned in `tests/test_crowding.py`: the half-width must clear the furthest occupied voxel PLUS `sqrt(3)`, because `rotate_volume` is trilinear and a voxel at radius R deposits density one voxel diagonal further out (cropping at R alone silently clipped 20% of a test blob), and the radius must be the exact furthest voxel rather than the bounding-box corner, which over-estimates by the corner-to-sphere ratio (254 voxels against 207 for 6bdf) and at 256 px rounds up to the whole box and buys nothing. The crop costs ~1.5e-5 relative in the image, from `grid_sample` normalising against a different half-width; no random draw moves, so the specimen stays seed-identical. (2) The ice convolution's chunked-FFT fix, see Physics Accuracy Notes. Together, 8 particles: 384 px / 2000 A 13.1 -> 11.0 s, 512 px / 2000 A 26.8 -> 17.5, peak memory unchanged; the win grows with box size because the template crop is a larger fraction there. Two things were measured and deliberately NOT done: `IceSlabBlender`'s pristine slab copy is ~1.5% and not worth further subtlety in that halo bookkeeping, and skipping the occupancy blur on pure-ice slabs does not apply, since with crowding on (the default) every z-slice carries density even at 2000 A although only 9.75% of voxels do.
- **Multislice runs on a 2x finer xy grid than the volume (`Propagation.oversample`, config `oversample`, default 2) and the exit wave is Fourier-cropped back.** The transmission function times the wave has twice the volume grid's bandwidth, and on that grid the excess wraps; across thousands of slices it compounds. Measured 2026-10-13 on a 6bdf particle at 1 A/px against a 4x reference: the volume-grid recursion (`oversample=1`, the old behaviour) was 0.2% of the scattered power in error in thin ice and 1.1% at 2000 A, 1.9% in the shells at Nyquist and 0.3% at low frequencies; the 2x grid with NO bandlimit is at the float32 noise floor (3e-7). Also converged at 2 for the strong-phase case, a rendered fcc gold bead (r = 50 A, cusps to 305 V/voxel) at 300 and 120 kV: 2, 3 and 4 all at <=5e-8 per shell against a 6x reference, where the volume grid shows 2e-3 to 5e-3 (the lattice fringes folding, the coherent analogue of the ice error). No regime in this domain has been found where 2 is not enough. Kirkland's `klim=0.66` is WORSE than leaving the aliasing in, 2% at low k, because what it cuts is real scattering that multiple-scatters back down, so `klim` stays `None` everywhere and is kept only for comparison. Cost: multislice time x2 at a 256 box, x2.7 at 512, x2.9 at 384 px / 2000 A ice (0.82 -> 2.37 s per particle), and about 0.17 GB per particle of fine-grid chunk temporaries at pad 512 (`memory.py`'s `_FINE_GRID_COMPLEX_COPIES` term); no volume memory, since slices are interpolated a chunk at a time. Both `Scattering` and `IterativeScattering` implement it. It is NOT multislice-only: Rytov and projection alias identically through their single final exponential (measured 1.2e-3 thin / 1.0e-2 thick, the same profile), so `_kernels.oversampled_exp` takes that exponential on the fine grid too, one fine-grid exp per image, which is what puts Ghostbuster's default Rytov forward model on the same footing as the simulator. First Born and `ctf` are linear and untouched; kinematic's per-slice `exp - 1` harmonics are ~N_slices times smaller and left alone. The resampler (`scattering/_kernels.py`'s `fourier_upsample_xy`/`fourier_crop_xy`) splits an even grid's Nyquist bin across +-N/2 -- without that the interpolation is not linear (`up(i x) != i up(x)`), which showed up as a 1.6e-3 disagreement between the absorptive and plain iterative loops. **The IMAGE is formed on the propagation grid too** (2026-10-14): `Scattering`/`IterativeScattering` take `crop=False` from every imaging object and return the fine-grid wave; `ExitWave.apply_ctf` builds the aberration module (`imaging._engines.aberration_engine`) at `pad_nxy * oversample` with `pixel_size / oversample`; `Detector(oversample=)` Fourier-crops the intensity to the pixel grid before anything defined on it (crop size, magnification, MTF, noise). A band-limited (Fourier) crop, NOT a 2x2 block mean: the measured camera MTFs already carry the pixel aperture, so integrating over the pixel here would count it twice. The reason is a measurement (`dev/crop_residual_probe.py`): `|psi|^2` has twice the wave's bandwidth and, in thick ice, cross terms with the scattering above the pixel Nyquist, and cropping the WAVE first lost 1.2e-3 (low k) to 1.8e-2 (Nyquist) of the image power at 2000 A -- the same size as the aliasing the oversampling removed. First Born's wave is interpolated onto the image grid in `imaging._stages.aberrate` for the same reason; `ctf`'s real projection is imaged linearly and stays on the pixel grid. `ExitWave.array` is on the image grid; `ExitWave.pixels()` and `Image.pixels()` give the PIXEL grid for callers. `TomogramReconstructor` does the same, which `tests/test_forward_model_parity.py` holds it to; `tests/test_modular_pipeline.py` is the explicit reference composition and also pins that cropping the wave first is a different image. The memory model's fine-grid term was not re-fit for this; the extra is one `(2 pad)^2` complex image per batch item. `dev/aliasing_klim_experiment.py` is the measurement; `docs/concepts/scattering/multislice.md` the write-up.
- **`ice_thickness` sizes the canvas and the ice, never the crowding slab.** It is a CONTRAST knob: raising it lowers contrast and deepens the solvent background. Until 2026-09-04 both particle simulators defaulted `crowd_max_distance_z` to `self.nz * pixel_size`, so it deepened the neighbour slab too and one field moved both the imaging conditions and the specimen -- 15 duplicates at 0 A against 76 at 2000 A (384 px / 1 A), which is also what two demo notebooks had been hand-setting to `None` around, commented "would result in too many particles above each other". The default is the TEMPLATE's own depth instead (`Specimen.crowd`: the template's `nz * voxel_size`, `nxy * voxel_size` from atoms), which is what the old expression already evaluated to whenever the ice fitted the box: a seeded 384 px run at `ice_thickness=0` is bit-identical across the change, and only the growth is gone. In a thick-ice box the neighbours now sit in the middle of the column and the rest is water. `MicrographSpecimenGenerator` still scales its with `nz`, and should: a micrograph is a specimen, a particle stack is a controlled image-formation experiment. Pinned in `tests/test_imaging_regression.py::test_crowding_slab_does_not_follow_ice_thickness` (and its `_from_atoms_` sibling); `configs/particle.toml`, `docs/concepts/pose-crowding.md` and the modular demo notebook, which re-derives the default inline, all state it. Do not "restore" the `nz` form for symmetry with the micrograph path.
- `pipelines/` — `run_particle_stack()`, `run_micrograph()`, `run_tilt_series()`, `run_build_tomogram()`, `run_build_ice_cache()`, `run_reconstruction()`: the actual end-to-end implementations behind the `cli/` commands, kept separate so `cli/` stays a thin argument-parsing layer. `_common.py` holds logic shared across them (device parsing, scalar-or-range sampling, exit-wave saving, etc.). `run_particle_stack` shards a multi-device run itself (`_ParticleRun`, `_generate_sharded`): contiguous index ranges go to spawned worker processes, one per device, each writing `particle_shard_<k>.pt`, gathered in order; per-particle seeding makes that stack identical to one device's. `run_micrograph` and `run_tilt_series` are single-device (see `cli/` above).
- **Multi-GPU comes in two flavours**, and both read the same `device` grammar. `devices.py`'s `parse_device` is the only parser; a pipeline calls it on `resolve_available_device(config.device)` (the one place a bare `"cuda"` degrades to the CPU) and picks the dispatch shape as a `DeviceSpec` method: `.devices` as the worker pool for pipelines that shard work units themselves (`run_particle_stack`'s index ranges, `run_build_ice_cache`, the gold-standard halves of `run_reconstruction`, the match probes; `run_tilt_series` rejects a multi-device string via `.is_multi`), `primary_and_pool()` for the tomogram renderer, and `lightning_target()` for `Ghostbuster.run`. There is no `"auto"`; a caller wanting every GPU names them.
- `specter build ice` (`pipelines/_ice.py`) generates a *replacement* `IceBank` library, for users needing ice at a pixel size or cell size the bundled `src/specter/ice_data/ice_cache` doesn't cover. It never writes into `ice_data/` (off-limits, shipped); output goes to `ice/`, which a simulation config then points `ice_cache_dir` at. Configs are named after their seed (`ice_config_filename`), not their batch position — that is what makes resume (skip files already present) and extension (re-run at a higher `seed_start`) both correct. The optimisation recipe itself is deliberately not exposed as config: `mlbop_target=-0.413` eV/atom and `mlbop_strength=0.5` are measured/validated properties of the phase of ice being reproduced, and a library mixing recipes would have `IceBank` drawing from several phases interchangeably.
- **`specter match particles` (`pipelines/_match.py`, package `match/`) derives a `ParticleStackConfig` that matches a real particle set** and writes it as `matched.toml` plus a Markdown/PNG report, without CryoSPARC anywhere in the loop. It drives the ordinary `run_particle_stack` for every probe, so the config it writes is exercised by exactly the code that will run it. Order of operations is load-bearing: (1) a pose-alignment check (noiseless render at the refinement's poses correlated pair-by-pair with the experimental images against a shuffled pairing) that stops the run on failure, because the 2026-09-01/02 EMPIAR-11377 sweep spent 60 classifications on poses rotated 142 degrees from the experiment and no rotationally averaged statistic could see it; (2) detector MTF/DQE(0), coincidence radius and dose envelope from the acquisition card only (`detector_model`, `dose`, `dose_rate`, `energy_filter` -- the four numbers no particle file carries), never fitted; (3) ice thickness and neighbour spacing from small probe stacks scored on the background variance outside the particle -- ALWAYS crowded (`crowd_candidates` must be positive multiples of the diameter, default [1.0, 1.3]; a no-neighbour candidate scored within noise of 1.3x and flipped between identical runs), and each probe keeps the FIRST entry of its candidate list (box-depth ice, one diameter's spacing) unless the best scorer beats it in 95% of a paired bootstrap over probe particles (`match.choose_probe`), because one setting scored 0.083 and 0.097 on two identical runs while candidates differed by <=0.03 and a plain minimum picked a different ice thickness on each of three runs; the report gives each score +- its bootstrap error and warns when a value is the fallback; (4) a two-seed comparison at matched poses whose headline is the per-band **matched-pose SNR ratio** (`match/_metrics.py::matched_pose_snr`), the one statistic that separated datasets that mixed in CryoSPARC from those that did not. The report says plainly when a residual remains that no forward-model parameter can close; on every dataset tried it tracked the absence of an energy filter. Do not add a B-factor, potential-scale or coincidence-radius *fit* to this pipeline: each was, in earlier hand tuning, a stand-in for missing physics, and the residual belongs in the report, not in a knob. The coincidence radius comes from `detectors.py`'s `EXCLUSION_RADIUS_PX` (physical pixels; Falcon 4i 2.0 px *with* DQE(0)=0.92 modelled, K2 2.54) and `HARDWARE_FRAME_RATE_HZ`, converted by `coincidence_radius_for_simulation` at constant occupancy per exclusion cell per frame -- it is a property of the camera unit, a prior for other units of the same model, and is treated as such.
- `specter reconstruct particle` (`pipelines/_reconstruct.py`) is the one inverse-direction command. It is also reachable as **`specter ghostbuster particle`**: `cli/_cli.py` calls `build_reconstruct_group()` twice, once per name, so the solver answers to the name the docs and the Python API call it by. Two group objects rather than one registered under two keys, since click fixes a command's `name` at construction and a shared instance would print whichever name was registered first regardless of what the user typed. A standalone `ghostbuster` console script is deliberately *not* the mechanism: PyPI already has a `ghostbuster` package (an unrelated AWS tool) whose install writes a `ghostbuster` entry point, so in a shared environment the later install would silently win.
- **`reconstruct`'s subcommand noun names the modality**, not the input or the output: `particle` is single-particle reconstruction, and the planned `TomogramGhostbuster` sibling is `specter reconstruct tomogram`. Singular for the same reason — a modality is not a count of inputs, so it does not follow `simulate particles`' plural. Do not "fix" the noun toward the input (`tiltseries`) or toward a uniform output (`map`); both readings look consistent in isolation and neither survives the pair.
- **Every `specter reconstruct particle` run is numbered and tracked through `specter.jobs`** — there is no untracked mode, the way neither RELION nor CryoSPARC has one. The directory is `output_dir/[project/]reconstructions/J00N/` — project comes right after `output_dir`, ahead of the `reconstructions` job-type subfolder, since users group their own work by project first, not by which pipeline produced it (`Job`'s folder shape generally is `base_dir/[project/]job_type/J0NN`; `_next_job_id` scans every job-type subfolder under a project, so numbering is one continuous sequence per project rather than restarting per job type). `project` (on both `ReconstructionConfig` and `Job` itself) is optional, not required: leaving it unset doesn't skip tracking, it just drops the project-name segment and uses `output_dir`'s implicit default project — pass `--project` to split one `output_dir` into several named ones, e.g. one shared scratch directory used across unrelated structures. `output_dir` (always a job-tree root here, since every reconstruction is tracked) defaults to `find_specter_project_root()` — which walks up from cwd looking for a `.specter` marker file, the same way `git` resolves the nearest ancestor `.git`, so running from a subdirectory of an already-initialised project lands in the same project rather than starting a disconnected new tree (and restarting numbering from `J001`). A `job.json` always records every parameter plus the git commit, and pinning `job_id` resumes into an existing directory (this is how a manual `halfset="A"` then `halfset="B"` pair shares one, with `Job.create` asserting every *other* setting matches). `lpp_params` (a nested table) is the one `Ghostbuster` argument with no config field, since it has no spelling a flag can carry.
- **`halfset="gold"` is the default**, not `"all"`: a bare `specter reconstruct particle` reconstructs halfsets A and B and computes the halfmap FSC between them (`fsc_gold_standard.png`, plus `resolution_gold_standard` in `job.json`), rather than one single-volume run. `pipelines/_reconstruct.py`'s `_run_gold_standard` opens the one shared `Job` exactly *once*, before spawning either halfset as a separate worker process (parallel across devices when `device` names at least two, sequential on one otherwise) — letting each worker open its own `Job` independently would race on `Job`'s auto-numbering, which does `_next_job_id()` then a bare `mkdir()` with no `exist_ok`. Workers never open their own `Job`; they only write into the path the orchestrator hands them. `halfset="A"`/`"B"` still reconstructs a single half (e.g. for a quick test), and `"all"` still reconstructs every particle as one volume, ignoring the split. **`cryosparc_ref` accepts a comma-separated `"<A>,<B>"` pair**, resolved per halfset by `config/_reconstruction.py`'s `cryosparc_ref_for_halfset` inside `_ghostbuster_kwargs`. It has to: `Ghostbuster`'s own docstring notes that `cryosparc_ref` is in `_job_log_exclude` precisely *because it differs between halfsets*, but a gold run derives both halves from one config, so a single path would put CryoSPARC's half-map A on half B's FSC figure under a `"CryoSPARC"` label — wrong, and silently so. Do not "simplify" the pair form away. A pair is rejected for `halfset="all"`, which has no second half to reference. **The half-map FSC is computed per epoch, not only at the end**: `Reconstructor._record_halfmap_resolutions` has whichever worker finishes epoch N *second* read its sibling's `epochs/<NNN>_<A|B>.mrc` off the shared run directory and compute the pair, writing `fsc_halfmap_<NNN>.png`. The epoch is claimed by creating that PNG with `O_CREAT | O_EXCL` -- the artifact doubles as the claim, verified atomic across processes on this project's NFS scratch mount (0/30 races in a direct test), so the two workers can never both compute the same epoch. Do not replace that with an `exists()` check, which is exactly the race it exists to avoid. The map-to-model FSC (`fsc_<NNN>_<A|B>.png`) was already per-epoch; it is the *half-map* one that used to appear only once, after both workers had exited. **Four resolutions are recorded per epoch**, masked and unmasked for each of map-to-model (FSC=0.5, via `Reconstructor._record_map_to_model_resolutions`) and half-map (FSC=0.143). The masked numbers come from `plots.resolution_between`, not from the figures: both plot helpers return the *unmasked* resolution even when drawing a masked curve. Every entry degrades independently rather than failing -- no `fsc_ref` drops map-to-model entirely (the half-map FSC needs no ground truth, it correlates A against B), no mask drops just the masked entries, and `_mask_for` also skips a mask whose shape doesn't match the volume, which is what a `test_run` produces since `bin_factor` bins the volume but not the mask or reference.

**`job.json` is the only JSON file a reconstruction run produces** -- there is no `params_<A|B>.json`, `metrics_<A|B>.json`, or `resolutions.json`. Both halfset workers hold everything (hyperparameters not already in the config, loss/lr history, per-epoch resolutions) in memory via `Reconstructor.results_summary()` instead of writing their own file, precisely because a run directory is normally on NFS, where `flock` **hangs** rather than serialising writers (verified: 80 locked writes from two processes did not complete in two minutes) -- two live worker processes cannot safely share one file. Do not "simplify" this back into a shared, locked file. `_run_single_halfset` sends its worker's summary back to the orchestrator through a `multiprocessing.Queue` when it exits (a spawned `Process`'s return value is otherwise discarded); `_run_gold_standard` merges both halfsets' summaries plus the gold-standard resolution into one `job.log(...)` call. Retrieval uses `_collect_halfset_result`, which *polls* the queue rather than blocking on a single `get()` -- a worker that crashes before ever calling `put` (an exception inside `_fit`, an OOM kill) would otherwise leave a blocking `get()` waiting forever, since nothing is ever coming; `_collect_halfset_result` instead notices the process has exited and returns `None`, so the existing `p.join()` + exitcode check downstream is what actually reports the failure. Do not replace this with a plain `queue.get()`. For the non-gold, single-halfset path, `results_summary()` is read directly off the model `_fit` returns, since that path never leaves the calling process and has no queue to cross. `job.log()` runs every value through the same recursive tensor-to-summary serialization `Job.create` already applies to constructor arguments (`_serialize_value`), since `results_summary()` can contain a raw `torch.Tensor` (e.g. `defocus_offset`). **`results` is nested by halfset label (`{"A": ..., "B": ..., "epochs": [...]}`) for `halfset="A"`/`"B"`, not just for `"gold"`.** This is what makes the manual two-pass workflow (`halfset="A"` then `halfset="B"` into the same `job_id`, in two separate process invocations) correct: each pass is its own `run_reconstruction` call with its own `job.log`, and `Job.log`'s merge is a plain `dict.update`, not recursive, so without nesting the second pass's call would silently replace the whole `results` value and discard the first pass's metrics -- even though `volume_A.mrc` is still sitting on disk right next to it. `_merge_halfset_results` (used by both this path and `_run_gold_standard`) reads `job.params` (the `Job.params` property, a snapshot of what's already recorded -- populated from the resumed `job.json` on the second pass) before folding in the new halfset, and rebuilds the merged `"epochs"` list every time so a two-pass run ends up with the exact same `job.json` shape as the one-command `"gold"` path. `halfset="all"` has no counterpart pass and keeps the flat, un-nested shape.
- **Output layout**: results land in per-artifact directories at the top of the working directory — `{particles,micrographs,tiltseries,tomograms,ice,reconstructions}` — resolved relative to cwd. There is deliberately **no `specter-data/` umbrella folder** (it existed until 2026-08-24); a project reads like a RELION or CryoSPARC one, with results at the top and a hidden marker naming the root. Path resolution is one rule with no special cases: an explicit path (TOML or CLI) is used verbatim and resolves relative to cwd; an omitted `output_dir` falls back to `config/_paths.py`'s `default_output_dir(artifact)`, still cwd-relative (not repo-root-anchored — that only resolves correctly for an editable install). `.gitignore` lists each artifact folder with a leading slash so `/particles/` doesn't also match a path inside `src/specter/`.
- **`.specter` is the project-root marker**, the way `.git` is a repository's and `.gui_projectdir` is RELION's. `find_specter_project_root()` walks up from cwd looking for it; `ensure_project_root()` is the find-or-create counterpart and **the only function here with side effects**. That split is load-bearing: a non-main DDP rank calls the pure lookup to agree on a path without racing its siblings to create anything, which is why `resolve_output_dir` takes `create=False` by default and only the process that owns the run passes `create=True`. Creation confirms at a TTY and auto-creates (printing a notice) otherwise — a blocking prompt would hang a batch job or CI forever, which is exactly why RELION pairs its dialog with `--do_projdir`. Nothing reads the file's contents; its presence is the whole signal.
- **The PDB cache lives outside any project**: `$SPECTER_PDB_CACHE`, else `$XDG_CACHE_HOME/specter/pdb`, else `~/.cache/specter/pdb` — the convention `torch.hub` and HuggingFace already use, which the `PDB_CACHE_ENV_VAR` comment had claimed to follow while actually defaulting per-cwd. One download is shared by every project instead of re-fetched per working directory, and an HPC user moves it to scratch with one export. **Everything in it is reproducible.** A structure supplied by path is read where it lies (`pdb.py`) and never copied in, which is what makes `specter cache clean` safe — nothing irreplaceable is ever in it. Do not "helpfully" copy user files into the cache; it would turn `clean` into a data-loss bug. Alongside the downloads, `parsed/` holds each structure's parsed form (atom positions, elements, bonded-species types), since parsing dominates the cost of loading an already-downloaded file: 16.7 s for a 220k-atom assembly against 0.09 s to read the arrays back, which took `specter build tomogram`'s structure-loading phase from 47 s to 12 s and the whole run from 2m43s to 2m8s. Those entries are derived, not originals, so the re-derivable guarantee is unchanged. Each is keyed on its source file's realpath/size/mtime plus every flag that changes the parse (`compute_atom_species`, `readd_hydrogens`, the resolved monomer library) and `_PARSED_CACHE_VERSION` — **bump that constant when changing `_build_typed_model`, `get_atoms_and_coordinates` or `get_atom_species`**, or stale entries will silently return structures the current code would not produce.
- **`specter cache dir|info|clean`** (`cli/cache.py`) exists because the cache is out of sight. A tool that hides a cache owes the user a way to locate and clear it, which is how `uv cache dir`/`clean` and `pip cache dir`/`purge` handle the same problem. `clean` confirms unless `-y`.
- **There is exactly one output-path field, `output_dir`, on every config** — a user should have one folder to point specter at, not one per layout. There is deliberately no `job_base_dir` (it existed until 2026-08-24 and was merged away; `ReconstructionConfig`'s was *renamed* to `output_dir`, so every command spells it the same). What the folder means follows from whether the run is tracked, which the user has already decided by setting `project`/`job_id`: untracked it is the leaf the files land in, tracked it is the root a `[project/]<job_type>/J00N/` tree grows under. So `--project` organises output *within* the chosen folder instead of relocating it. `pipelines/_common.py`'s `resolve_output_dir` is the single place this resolves, and it is the only thing that should ever read the raw field. Two consequences not to "clean up":
  - **`output_dir` defaults to `None`, not to a computed string.** The two unset defaults genuinely differ — `<artifact>/` untracked, `find_specter_project_root()` tracked — because the tracked layout supplies its own `<job_type>` segment. Baking `tomograms` into the field would produce `tomograms/tomograms/J001`. The default is not knowable until tracking is, which is why it resolves at use time.
  - **Nothing rejects `--output_dir` alongside `--project` any more, and nothing should.** An earlier pass added a `reject_output_dir_with_tracking` guard; merging the two fields deleted the conflict it existed to catch. Combining them is now the ordinary case.
  The CLI shows `output_dir`/`filename` and the tracking flags in one `Output & job tracking` panel, so the two remaining directory flags per command (`--output_dir`, `--pdb_cache_dir`) are visibly an output and an input cache rather than three interchangeable paths. `--pdb_source` (renamed from `--pdb_code` on 2026-08-24) is the same vocabulary the tomogram config's `[[targets]]`/`[[filler]]` tables already used, and it takes a local path as readily as an accession code — the old name told a user with their own structure that they were out of luck. `specter jobs --base_dir` keeps its own name: it reads an existing tree rather than choosing where to write.

## Physics Accuracy Notes

- **The free-space propagator is `exp(-i pi lambda dz k^2)`** (`scattering/_kernels.py`'s `fresnel_propagator`, and the first-Born-family stack in `_batch.py`), paired with the transmission `exp(+i sigma V dz)` and the transfer function's `exp(-i chi)`: propagating a distance d downstream is overfocusing by d, because an underfocused lens images a plane upstream of the specimen. Until 2026-10-16 it was the conjugate, which gave the right single-scattering image but walked depth the wrong way (its exact equivalent was the image of -V at overfocus with negative Cs). The fix keeps every `ews_curvature_sign` label's curvature: `"negative"` (default) now walks slices 0 -> nz-1, the beam entering at slice 0, `"positive"` the reverse, and `defocus_midplane_shift`/`tilt_defocus_shift` are now NEGATIVE (minus half the depth: the exit face is the high-defocus end). First Born, projection and `ctf` images are unchanged; multislice and Rytov change at second order. Validated on EMPIAR-10083 with the J005 Rytov settings: same curvature 3.562 A against 3.563 (maps correlate 0.99994), curvature mirrored 3.981 A, so never z-flip V to 'fix' this; and against an independent Kirkland-convention multislice to float precision (`tests/test_scattering.py::test_multislice_matches_an_independent_physical_reference`, which the old sign fails at 2.2e-3). The surface rotate mode's paraboloid keeps its `k_z` per label; only its constant phase followed the propagator.
- Electron wavelength is computed relativistically — do not use the non-relativistic approximation.
- The interaction parameter `σ` is energy-dependent; always use `interaction_parameter()` from `constants.py` (re-exported by `specter.scattering`).
- **Which parameterization applies depends on what is being rendered, and this is not a tidiness problem to unify.** Shtyrov fits bonded species of *biomolecules*, over a tabulated range of 0.011-0.62 1/A. Bulk materials are outside that domain, and a mean inner potential is a k=0 quantity, so reading one off those fits extrapolates below their own data -- visibly: `H(C)`'s tabulated values are negative below ~0.2 1/A. So there are two config fields, not one: `scattering_factors` (default `shtyrov`) governs anything with bond topology -- targets, filler, filaments, microtubules, transmembrane proteins -- and `bulk_scattering_factors` (default `kirkland`) governs ice, the carbon film and gold fiducials. Measured against holography: ice is expected near 4.21 V (scaled from liquid water's 4.48 +/- 0.19 V, Yesibolati et al. 2020) where the rendered ice gives 4.55-4.58 V under kirkland (0.5-1.5 A voxels, at the library's 0.94 g/cm^3; continuum 4.59 V) and shtyrov 3.63-3.67 V; for carbon, kirkland/lobato/peng agree to 0.5% while the `C(CCC)` proxy sits ~40% above all three. A membrane's bilayer takes neither field -- it builds from bare lipid coordinates, so every atom is per-element Peng. The two fields were briefly coupled on 2026-08-28 ("one setting everywhere") and had to be uncoupled again; do not re-merge them.
- **Shtyrov needs bond topology to be worth using.** It fits scattering factors per *bonded species* (`"C(HHHC)"`), so without `atom_species` every atom silently falls back to per-element Peng `c4322` factors — real published factors, but not what `parameterization="shtyrov"` implies. Every path that builds a `PDB` and renders it therefore passes `compute_atom_species=True` when (and only when) the parameterization is `shtyrov`, and forwards `pdb.atom_species` into `PotentialBuilder`: `TomogramSpecimenGenerator` (protein/filament/microtubule templates), `render_transmembrane_template`, `run_particle_stack`, and `run_micrograph` (which silently rendered 100% Peng until 2026-08-19 — it built a default-`shtyrov` `PotentialBuilder` with no `atom_species` at all). Typing costs ~1.3 s per unique structure (36k atoms) and changes a rendered template by ~4% relative RMS. Structures with no resolvable topology (legacy PDB format, isolated ions) degrade per-atom on their own — do not add a global guard for them. Paths that build potentials from bare coordinates (`Specimen.from_atoms`, `membrane/_profile.py`'s lipid model) have no bonds to type and correctly stay per-element.
- **Shtyrov typing is hydrogen-limited without a Monomer Library.** 20 of the 42 species name an H neighbour, and a descriptor is built from atoms actually in the model, so in a hydrogen-free deposition a methyl carbon reads `C(C)`, not `C(HHHC)`, and misses the table: ~44% of a protein falls back to Peng (measured on 1A6M; 56% -> 99% coverage with a library). Supplying H needs the [Monomer Library](https://github.com/MonomerLibrary/monomers) via `$CLIBD_MON` or `PDB(monomer_library_path=...)`; it is deliberately **not** packaged (1.5 GB, LGPL-3.0, and specter is All Rights Reserved) — users install it themselves, see `docs/installation.md`. When one resolves, `PDB` takes `atomic_numbers`/`coordinates`/`atom_species` from the single H-completed gemmi model (`_build_typed_model`) instead of reconciling Biopython's atom list against gemmi's, which is what made the two disagree and raise. Rendered potential shifts 20-30% relative RMS. `readd_hydrogens` defaults to `"auto"`: hydrogens a file already carries are kept where deposited (there is no reason to move information the file provides), and only a structure with none has them added. `True` always re-adds from ideal geometry (sffit's default, the configuration the factors were fitted in); `False` never adds density, backfilling only zero-occupancy typing dummies -- which still lifts 1A6M from 56% to 99.2% typed with the atom set unchanged, since a descriptor comes from the bond graph, not from positions. Three rules are copied from `sffit` (the reference implementation, at `~/sffit`): drop `occ == 0` atoms (gemmi zero-occupancies ambiguous H — rotatable hydroxyls, *both* His tautomers — which would otherwise render at full weight since `PotentialBuilder` has no occupancy weighting), drop `ConnectionType.MetalC` links (heme Fe types `Fe(NNNN)` instead of the untabulated `Fe(NNNNNOO)`), and restore `st.connections` between the two `prepare_topology` passes. Both of the first two apply **only** on the library path: without a library, dropping metal links degrades Fe to `Fe(NNN)`/`Fe(N)`, and dropping `occ == 0` would desync from Biopython. `expand_ncs` and sffit's altloc handling are deliberately not copied — specter fetches RCSB assemblies (would double-expand) and renders without occupancy weighting (would double-count conformers).
- **Anisotropic magnification is a band-limited resampling, not an interpolation of the pixel grid** (2026-10-18; `microscope.Detector.anisomagnify`, used by every simulator and both reconstructors). Each image's trigonometric interpolant (its DFT coefficients) is evaluated at the warped pixel positions `A (x - c) + c` by one type-2 NUFFT (`nufft.sample_transform`, which now takes 2D grids and a batch sharing its points); the matrix keeps `affine_grid`'s normalised-coordinate meaning and the `(N - 1) / 2` centre. The bilinear `grid_sample` it replaced damps a frequency `f` by `|1 - t + t exp(2 pi i f)|` at fractional offset `t` (0.16 at 0.45 cycles/px, t = 0.5), and a 0.9% anisotropy reaches a pixel of offset across a big particle, varying over it -- which was the whole of Ghostbuster's gap to CryoSPARC's Ewald-corrected maps on anisomag datasets: EMPIAR-10551 1.660 -> 1.616 A (CryoSPARC 1.618), map-to-model 1.812 -> 1.795 A; EMPIAR-12391 2.221 -> 2.185 A (CryoSPARC 2.190). On P22 (EMPIAR-10083, ~0.2% per axis, bands at 0.33-0.44 cycles/px) it is a reproducible trade rather than a gain: map-to-model better in every band (0.651 against 0.645 at 4.5-3.6 A), half-map FSC slightly lower (3.327 against 3.278 A, two runs each). Two traps, both measured: sampling the image's discrete-space transform at `A^-T k` instead treats the image as zero outside the box, so the box edge rings across the image (5% error on a test blob); and the matrix direction matters (`A^-1` collapses the held-out high-resolution FRC). `tests/test_anisomagnify.py` pins the analytic warp (square and not), a near-Nyquist fringe (bilinear is 0.40 off), the old convention and the adjoint. The resampling is periodic: content moved past an edge re-enters at the other.
- Coincidence loss is modelled for direct electron detectors — do not remove this when simulating K3 detector outputs.
- CTF sign conventions follow the standard cryo-EM convention (defocus positive = underfocus).
- Detector MTF and DQE(0) are separate physical effects and must stay separate: bundled detector MTFs are derived from published DQE curves, so the shape is normalised as `sqrt(DQE(k)/DQE(0))` (`detectors.py`), and the zero-frequency counting efficiency is applied separately via `Detector(dqe0=...)` by scaling expected electron counts. Folding `DQE(0)` into the MTF instead would scale counts by `sqrt(DQE(0))` rather than `DQE(0)` and give the wrong shot-noise statistics.
- `IceBank` tiles volumes larger than a single cached config in **coordinate space**: it draws multiple independently rotated/translated crops (`_place_tiles`), places them side by side, and heals the tile boundaries with a short local MLBOP relaxation (`_relax_seams`) rather than voxel-space blending — do not replace this with a plain repeat/tile or hard-edge concatenation, which would leave visible seams (and, unrelaxed, measurably unfavorable energy at the boundaries). Relaxation cost is bounded to a halo band around each seam (`_place_tiles`'s `halo_margin`; only halo atoms are fed to the energy model, the untouched bulk is reattached unchanged), and is off by default — `generate_big_ice`/`generate_big_ice_deltas`'s `relax_steps` (exposed as `Ice.relax_steps`, config `ice_relax_steps`) defaults to 0. `generate_big_ice` is also memory-bounded for very large volumes. `tile_volume_from_blocks_blended()` (in `arrays.py`) is a separate, still-used utility for **voxel-space** tiling — overlap-add with random roll/flip/rotation augmentation per tile — used by `MDSimDump`/`ExtXYZDump` to assemble MD trajectory frames into larger volumes, not by `IceBank`. `RandomIcemaker`/`GradientSKIcemaker` only produce single unique blocks (`generate_ice`); they don't assemble large volumes themselves.
- Ice structure is driven by `GradientSKIcemaker` (optimised against pre-computed S(k)/MLBOP targets in `src/specter/ice_data/`) and cached via `IceBank`; `RandomIcemaker` is a fast, low-fidelity fallback for quick tests.
- **Ice renders one site per water molecule, and that site is a whole molecule.** `ice/_kernels.py`'s `build_water_kernel` is oxygen plus two hydrogens smeared over a spherical shell at the 0.9572 A O-H distance -- not a bare oxygen, which is what specter rendered until 2026-08-28 and which put ice at 2.08 V under the then-default shtyrov (2.95 V under kirkland) against a measured ~4.21 V, roughly half the real scattering. Hydrogen is not negligible for *electrons*: Mott-Bethe makes a diffuse one-electron atom disproportionately strong at low k, so two H are 43% of a water molecule at k=0 and still 26% at 1.5 A. The shell is load-bearing and costs nothing (one Fourier multiply by `sinc(2*pi*k*R)`): molecules are randomly oriented, so a hydrogen's contribution decoheres with k, and collapsing it onto the oxygen instead gives the identical mean inner potential while carrying ~1.9x the ice power from 5 A to Nyquist. Do not "simplify" it to `K_O + 2*K_H`. Hydrogen resolves through the ordinary fallback rather than a special case: the Shtyrov tables have `O(HH)` but no `H(O)`.
- **Potential kernels are odd-sized and voxel-centred, and the ice canvas is convolved periodically.** `compute_supersampling_parameters` keeps the super-sampled grid EVEN (no sample at the 1/r origin, which is what made Kirkland blow up on an odd fine grid) and the pooled kernel ODD, doubling an odd super-sampling factor so both hold. Until 2026-09-02 the pooled size fell out of the fine-grid rounding and was even for 20 of 36 pixel sizes (0.731 A gave 8^3, 1.5 A gave 4^3; 1.0 A happened to give 5^3), and an even kernel has no centre voxel, so every `method="3d"` potential landed half a voxel off its coordinates. On the ice canvas that combined with a linear 'same' convolution to leave the low face plane at HALF its potential and the high face at 92%; solvate's reflect padding then mirrored that into a dark line at the box boundary on every slice, which the CTF turned into a rim and ring scaling with ice thickness (the artifact was in every simulated particle, and grew when the hydrogen shell widened the kernel). `potential_from_deltas(boundary="periodic")` wraps instead, used by both `IceBank` canvas builders: a canvas is a piece of bulk, not a molecule in a box, and within a kernel radius of a face the wrapped neighbours have the status of an unrelaxed tile seam. Proteins keep `"linear"`. `tests/test_ice_canvas_faces.py` pins face-plane uniformity, the centroid, and the grid parity rules; do not "simplify" the parity rules back to a plain even/odd choice.
- **A periodic convolution's z-chunks read a halo, and `out=deltas` aliases it.** Past `_DELTAS_FFT_MAX_VOXELS` (2^28) `potential_from_deltas(boundary="periodic")` convolves a z-chunk at a time, each chunk gathering a halo of real neighbouring context that wraps at the faces. `IceBank.generate_big_ice` passes `out=deltas` so the potential overwrites the deltas rather than taking a second canvas -- which is safe whole-canvas, where each item is read in full before it is written, and was NOT safe chunked: the halo reached backwards into the previous chunk's output, the wrap reached back into the first chunk's, and both got convolved a second time at ~956 V against ice's 4.6. Measured on a seeded `simulate particles` at 384 px / 1 A / 2000 A ice, that was 18% of the image in max and 29% in RMS against a never-chunked reference, with two baseline runs bit-identical. It fired whenever `nz * nxy^2 > 2^28` -- ice thicker than roughly 4096 A at 256 px, 1820 A at 384, 1024 A at 512 -- so never at the shipped 256 px defaults, and reached `blend_ice_into_volume`'s device branch (tilt series, micrographs) as well as particle stacks. Fixed 2026-09-04 by stashing the `kz - 1` pristine slices the halo needs: a rolling `tail` for the chunk boundaries and a `head` for the wrap. Both must roll across SEVERAL chunks, since a chunk can be shorter than the halo, and the wrap fix-up triggers on `z1 + n_head > nz` rather than on the last chunk, or a short chunk near the end still corrupts. The volume cap now sizes that chunk instead of deciding the backend, so a canvas too large to transform whole is still transformed a chunk at a time (`_deltas_backend` takes `boundary`; `"linear"` has no such loop and still falls back to conv3d): 84 ms against conv3d's 168 at 2000 x 384^2. The FFT's chunk is a QUARTER of the cap, since it holds both operands' complex transforms at once -- handing it the whole cap took a solvate's peak from 9.3 to 12.6 GiB to save 0.6 s. `tests/test_potential.py::test_periodic_deltas_chunking_matches_whole_canvas` pins every combination against the whole-canvas transform. It parametrises ODD kernels only, on purpose: for an even kernel the two branches sit a voxel apart, a pre-existing gap between the rolled-kernel origin (`k // 2`) and `spatial_convolve3d_same`'s centred crop (`(k - 1) // 2`) that nothing can reach while `compute_supersampling_parameters` keeps every kernel odd.
- **The bilayer's `psi(z)` is a plane average, and anything compared against it must be one too.** `membrane/_profile.py`'s profile is looked up by signed distance, so every value in it is the mean potential over a plane at height z, not the value at an atom's centre. There is no amplitude scalar in the live path -- `generate()` renders the measured `psi(z)` as-is -- but until 2026-08-30 one was fitted against an isolated atom's peak, which overstated the bilayer 5.1x. No `voxel_size` fixes that: a cusp has no grid-independent value, phosphorus reading 400.5 V at 0.5 A, 26.9 at 2.0 and 4.1 at 4.0. The rationale on record, that a plane average dilutes the peak ~20x, measured the FULL reference patch; `compute_bilayer_profile`'s `lateral_core_fraction=0.6` window excludes the under-populated jittered edges and recovers 64.9 A^2 per lipid against the patch's own 65.0 target. `CALIBRATION_VOXEL_SIZE_ANGSTROM` is the grid the patch is rendered on, decoupled from the render voxel size on purpose; resolution loss is applied once, later, by `_raster.py`'s anti-aliasing. It is scaffolding for a synthesized profile and disappears if `psi(z)` is ever sourced from MD or published density profiles. Its exact value is loose because the shipped quantity is the whole curve: over 0.25-2.0 A the integral spans 0.7% with no trend, while the PEAK spans 7.70-8.59 V non-monotonically -- grid-alignment scatter on a narrow feature, not a convergence sequence, so don't read a converged peak off it. The amplitude-fitting helpers and the analytic two-Gaussian profile they scaled were deleted on 2026-08-31 once nothing called them; `test_plane_average_is_not_an_isolated_atom_cusp` measures both quantities directly rather than keeping functions alive to host the check.
- **A bilayer's ground truth is a slab with headgroup bumps, not two lines on vacuum.** The "railroad track" is an *imaging* signature -- CTF phase contrast on a density gradient -- so building it into the specimen both double-counts it and deletes the acyl core, which really holds hydrocarbon at 5.4 V. That cost 4.8x of the bilayer's integrated potential at the template's native 40 A thickness (4.4x at the generator's 37 A default): invisible in a slice, where the headgroup peaks dominate, and dominant in a projection, which is how it survived unnoticed. The lipid template is exact POPC stoichiometry, C42 H82 N O8 P; it carried 31 C and no hydrogens until 2026-08-30, 59% of real scattering. Hydrogen is load-bearing for the same Mott-Bethe reason as in the ice kernel above, and is why the acyl core sits **above** amorphous ice (5.4 V against 4.6) even though hydrocarbon at 0.9 g/cm^3 is the less dense material -- reasoning from mass density gets that sign wrong. The chain is pinned by one parameter-free identity, `integral(psi dz) == 2 * (scattering per lipid) / (area per lipid)`: 254.0 V*A measured against 254.5 predicted, asserted in `test_bilayer_profile_integral_matches_popc_stoichiometry`. The per-leaflet z-offsets are still hand-picked, and are the next thing to fix: they put the template's own phosphate spacing at 40 A against 35-38 A measured for fluid phosphatidylcholines (POPC 37.0 A, Kucerka et al. 2005).
- **How much ice a voxel gets is decided by how full that voxel already is, and the potential is asked that question at the WATER's length scale, not the nucleus's.** `potential/_occupancy.py`'s `potential_occupancy(V, voxel_size)` coarse-grains `V` over `WATER_COARSE_GRAIN_SIGMA_ANGSTROM = 2.0` A and returns `clamp(blur(V)/FULL_OCCUPANCY_POTENTIAL_V, 0, 1)`; `blend_ice_into_volume` scales the ice field by `1 - occupancy`. **Sigma is in ANGSTROM, and that is the whole point** -- a per-voxel width would put the grid back into the answer. Two rules preceded it, both wrong, and neither should return. `V < 0.05 * V.max()` (until 2026-08-31) was relative to the volume's own contents, so adding gold fiducials to a 1000x4000x4000 A specimen took `V.max()` from 17.85 to 35.18 V and the fraction of occupied voxels receiving ice ON TOP of themselves from 12.9% to 28.8%; it altered ice on 13.87% of all OTHER voxels when one synthetic gold blob was added and nothing else changed. Unblurred `clamp(1 - V/7)` (until 2026-09-01, spelled `ice_occupancy_weight`, now DELETED) fixed that and left a worse one: a potential is cusped, so it finds the boundary of every ATOM rather than of the MOLECULE and pours bulk ice into the gaps between BONDED atoms 1.5 A apart. Measured on 1A6M at 1 A/voxel it admitted 0.597 of full-strength ice into voxels solidly inside the protein, and the excluded volume it recovered ran 0.36 of the molecule's own volume at 0.75 A/voxel to 0.87 at 4 A -- a 144% spread, against 0.9% blurred. The blur is not an extra approximation: a coarse voxel's own average has already removed the cusps, so raw and blurred agree exactly beyond ~8 A and the convolution is SKIPPED below a quarter voxel (at 10 A/voxel it is a no-op, correctly). It reads past whatever slab it is given, so `blend_ice_into_volume` widens each z-chunk by `occupancy_blur_halo_voxels` and discards the margin; without that every chunk boundary prints into the ice as a seam. `FULL_OCCUPANCY_POTENTIAL_V = 7.0` is protein's mean inner potential (6.81/7.00/7.07/6.84 V across 1A6M/1FA2/7VD8/6QZP); it lives in `potential/_occupancy.py` beside its provenance and two open caveats and is re-exported from `specter.ice`, so do not add a second copy -- it rests on the standard partial specific volume 0.73 cm3/g, a thermodynamic rather than geometric volume, and unlike the ice value it has no external citation. Gold and carbon sit far above it, clamp to zero and exclude water outright; a partial-volume voxel at a particle's edge takes partial ice, which is what belongs there. One reference serves every material because the blend sees a single summed volume: material lighter than protein is under-excluded (a bilayer's acyl core keeps ~23% of its water), which is bounded and one-directional.
- **Partial temporal coherence is an incoherent sum over defocus, not an envelope on the wave** (2026-10-14). With `cc` set, `ExitWave.apply_ctf` builds the transfer function WITHOUT the Cc envelope and `ExitWave.intensity` forms the intensity as `sum_i w_i |psi * exp(i pi lambda k^2 d_i)|^2` over a Gauss-Hermite quadrature of the focal spread (`aberrations/_coherence.py`'s `FocalSpread.intensity`, the ONE implementation of the sum: `ExitWave.intensity` and `Detector.intensity`, which the frozen-plasmon loop uses, both call it). The envelope is exact for the linear term only; the quadratic term needs the transmission cross-coefficient, which damps a pair by `exp(-(pi lambda sigma_f)^2 (k1^2-k2^2)^2 / 2)`, not by `E(k1)E(k2)`. Measured (`dev/tcc_experiment.py`, 6bdf 1 A/px, Cc 2.7 mm, 0.7 eV): 2000 A ice at 300 kV the envelope is 0.4% low in mean (it loses electrons) and 0.7% low in power below 10 A; box-depth ice <0.05%; 120 kV 5.1% low in mean, 4-14% off in power. Node count from `a_max = pi lambda sigma_f min(1/(s dx^2), 1/(2 dx^2))`: 16 at 300 kV, 91 at 120 kV; capped at 300 because numpy's `hermgauss` returns NaN weights somewhere between 300 and 400. Validated: `tests/test_focal_spread.py`'s three-beam case (the +k0/-k0 second harmonic is exactly undamped by any focal spread; the envelope damps it by E^2) and `dev/abtem_tcc_check.py` against abTEM HEAD's weighted defocus ensemble (8e-10). Do NOT cross-check against PyPI abTEM 1.0.10: it weights the wave AMPLITUDE by the distribution weights, so its intensity sees a sigma/sqrt(2) Gaussian; fixed on their main. `Envelopes(temporal_coherence="envelope")` restores the old route; the linear `ctf` model keeps the envelope (exact there). **Cc is ON by default for the forward simulators since 2026-10-14**: `ExitWave.intensity(cc=2.7)` (mm), `settings.DEFAULT_CC_ANGSTROM` (2.7 mm, Titan Krios) in `Envelopes.cc`, `cc = 2.7` (mm) in the particle/micrograph/tilt-series configs, `energy_spread` 0.7 eV; `cc = 0` (or None) disables it. The coherent image it replaced had +15% power at the Nyquist shell at 300 kV / 1 A/px (x8.7 at 120 kV). It applies to energy-filtered data too: the source's spread passes any zero-loss slit, and the filter only removes inelastic electrons. The INVERSE stays Cc-free on purpose: `Reconstructor.forward` and `TomogramReconstructor` call `intensity(cc=None)` explicitly, because the default would otherwise be the forward one (the ghostbuster golden fixtures pin this -- they must NOT move when the forward default does). `specter match particles` takes `cc`/`energy_spread` on its acquisition card (no particle file carries them), applies them to every probe, reports them and writes them to `matched.toml`. Keep `DEFAULT_CC_ANGSTROM` in settings.py: importing it from `specter.aberrations` pulled torch+Lightning into `import specter.settings` (0.2 s -> 8.5 s).
- **Under exposure the solvent decorrelates; only the specimen is damaged -- when asked to.** Raw EER movies show the 3.7 A water ring flat across 50 e/A^2, so the GG2015 envelope on the transfer function (the default, `Envelopes(dose_envelope_target="transfer_function")`) wrongly fades the ice with the protein. `dose_envelope_target="specimen"` (particle, micrograph and tilt-series generators) damages the specimen's 3D potential before solvation, with occupancy read from the UNDAMAGED specimen (`free_fraction_field`) because the envelope spreads the potential and a damaged read let 19% ice into a protein core. `Ice(motion_variance=sigma0^2)` then filters the ice fluctuation to what survives the summed exposure (`ice/_exposure.py`, mean kept, applied before the particle's hole is cut); it is refused alongside an envelope on the transfer function, in the config validator and the generator. The default coherence model is `"relaxed"`, compressed-exponential curves measured grid-free on kick+relax trajectories and normalised to McMullan's Gaussian model by correlation AREA at the 3.7 A ring; long wavelengths decorrelate 12-36x faster than independent kicks. Both features are OPT-IN and the defaults are bit-identical to before: the specimen path's effect on matching real particle stacks, and the sigma0^2 motion-corrected data support, are still being validated. `fft.apply_radial_envelope_` is the one chunked 3D radial filter both use.
- **A geometric occupancy field, built from van der Waals radii, was tried and REMOVED on 2026-09-01** (recover it from 8599e49). It is sharper -- 0.006 of full ice inside a molecule against the blur's 0.211 -- but it changes nothing any specter output can see, because a Gaussian blur CONSERVES the integral of V and therefore the total displaced water; it only moves where the displacement sits, taking too little from the interior and putting the same amount into a halo just outside. Measured on a ribosome column: 2170.8 V*A of ice under the blur against 2171.3 under geometry, 0.02% apart. Every shipped artifact either integrates along a ray (single-particle images, and tilt series -- the blur is isotropic, so conservation holds at any tilt) or carries no ice at all (`specter build tomogram` writes a clean volume plus labels; ice enters only at `simulate tiltseries`). It also cost more than it looked: combining it with the blurred field by `max` OVER-excluded by 2.2%, since that keeps the blur's halo artifact and the geometric interior at once. Do not reintroduce it unless a ground-truth volume ships WITH ice in it, which is the one case where the redistribution stops cancelling.

## Reproducibility

- Use `specter.seed(n)` (re-exported from `random_seed.py`) to set a global seed before any simulation. It controls every draw specter makes, but **it does not make a run bit-reproducible**, and the gap is larger than float noise suggests.
- **A seeded particle stack is a function of `(seed, particle index)`, not of how it was batched** (since 2026-10-13). `Specimen.scatter(seed=)` and `Image.detect(seed=)` take it, and each particle's crowding, ice draw and detector noise come from a generator seeded by `random_seed.derive_seed(seed, poses.ids[i], stage)` (NumPy `SeedSequence` under the hood, abTEM's practice; stages are `imaging._stages.SEED_STAGE_*`): one batch of six, two of three and six singles give the same stack bit for bit on CPU, and one or several worker processes give the same stack (`tests/test_particle_base.py`, `tests/test_imaging_particles.py::test_a_slice_of_the_stack_draws_what_the_stack_drew`, `tests/test_pipelines.py::test_run_particle_stack_seed_reproduces_across_batch_sizes`). That is why `batchsize="auto"` is no longer refused alongside a seed. A seed is an argument to each call, not object state, so a shard needs nothing broadcast. Three mechanisms, chosen per stage: the detector takes an explicit `torch.Generator` through every draw site (no global state touched); `IceBank` already took a `generator`; the crowd's draws go through roma and the Poisson-disk sampler, which take none, so they run under `random_seed.seeded_rng`, a CPU-only `fork_rng`. Without a `seed` (the direct-API default) everything still comes off the global stream and batching decides which draw reaches which particle. A micrograph is seeded per index too (`Field.draw(seed=, index=)`, stage `SEED_STAGE_SPECIMEN`), and a tilt's noise per `(seed, id, detector stage, tilt)`. The forward model is non-deterministic at ~2e-5 relative, from GPU reduction and FFT ordering, and Poisson sampling then DISCRETIZES that: most pixels round to the same integer count, a few cross a boundary and jump. Measured on a seeded `specter simulate tiltseries`, two identical runs differ on 0.1% of pixels by up to 74 counts; the same config at `noise_model="none"` differs on 98.8% of pixels but only at 2.1e-5 relative. `specter build tomogram` is likewise not bit-reproducible at a fixed seed, because its species are rendered in parallel and accumulated in a non-deterministic order (29% of voxels differ, at 6e-6 V on a 24 V volume). Both are inherent unless `torch.use_deterministic_algorithms(True)` is forced, which costs performance and is not set. What a seed DOES guarantee is that the specimen -- which species, how many, placed where -- is identical, and every one of those is exact: labels, picks and region volumes come back byte-identical run to run.
- **When A/B-ing a change for reproducibility, always run a baseline-vs-baseline control.** Two runs of the SAME code differ by the amounts above, so a comparison without that control reports the noise as a regression. This is not hypothetical: it made a 29%-of-voxels "difference" look like a real change until the control showed identical numbers.
